# Folio — A Lightweight Collaborative Document Editor

Folio is an intentionally focused full-stack document editor. It provides a document dashboard, browser-based rich-text editing, automatic saving, `.txt` imports, and sharing between three seeded demo accounts. The app uses a Python HTTP server, plain JavaScript, and SQLite locally; it also supports PostgreSQL for durable deployment on Render.

## Features

- **Create and rename documents**; reopen documents after refresh.
- **Rich-text editing:** bold, italic, underline, headings 1/2, numbered and bulleted lists, and remove formatting. Browser-native `contenteditable` and formatting commands keep the dependency footprint small.
- **Autosave:** debounced ~700 ms after the last edit; visible save status.
- **File import:** UTF-8 `.txt` only (maximum 1 MB); each upload becomes a new editable document. Unsupported or malformed files return useful validation errors.
- **Sharing:** the owner grants `Can edit` or `Can view` access to other seeded demo accounts and can revoke access. Dashboard separates owned and shared documents. Demo user switching makes the full flow reviewable.
- **Persistence:** SQLite on disk locally and PostgreSQL when `DATABASE_URL` is configured.
- **Safety and reliability:** allowlist HTML sanitization, CSRF validation, owner/editor/viewer checks on the server, request length limits, and document revision checks to prevent accidental stale overwrites.

## Run locally (Python 3.10+)

```bash
python server.py
```

Open **http://localhost:8000**. There are **no mandatory pip dependencies** for local SQLite operation.

The application automatically initializes the database in `data/folio.db` and seeds these three demo accounts:

| Name | Email | Demo use |
|---|---|---|
| Anjana Prasad | `anjana@example.com` | Create and share documents |
| Alex Morgan | `alex@example.com` | Receive `Can edit` permission |
| Priya Shah | `priya@example.com` | Receive `Can view` permission |

**Test the sharing flow:** Create a document as Anjana → click Share → invite Alex (Can edit) and Priya (Can view) → switch demo accounts using the bottom-left selector → verify that Alex can edit and Priya cannot. These are *demo personas*, not authenticated real accounts. The user switcher should never be presented as production-grade identity verification.

To configure a custom local database or port:

```bash
DATABASE_URL=sqlite:////absolute/path/to/folio.db PORT=8080 SECRET_KEY=replace-me python server.py
```

The `data/` directory is not included in the ZIP; the application creates it automatically.

## Automated tests

```bash
python -m unittest discover -s tests -v
```

Six end-to-end HTTP tests cover create/save/reopen, role enforcement, unshared access denial, stale revision conflicts, file uploads, sanitization, and CSRF protection.

## Render deployment

The repository includes `render.yaml` with a **free web service** and **free PostgreSQL database**. Render's free service may cold-start after inactivity, and free database plans may have lifecycle restrictions. Confirm limits in your Render dashboard before using this beyond evaluation.

1. Push this project to a **GitHub repository** connected to Render.
2. In Render: **New → Blueprint** → select the repository and `render.yaml` → review resources → apply.
3. Render provisions PostgreSQL and sets `DATABASE_URL` from the database connection string automatically. `SECRET_KEY` is generated by Render.
4. Wait for a successful deployment; open the assigned `https://…onrender.com` URL.
5. Test create → edit → refresh → share → switch account on the live URL, then paste that exact URL into `SUBMISSION.md`.

Alternatively, create a Render web service manually: Python runtime, build command `pip install -r requirements.txt`, start command `python server.py`, health endpoint `/health`, `PORT` supplied by Render, and environment variables `DATABASE_URL` and `SECRET_KEY`. `DATABASE_URL` must point to an accessible PostgreSQL instance; the optional dependency `psycopg2-binary` is listed in `requirements.txt`.

**Important:** Render's free web-service filesystem is ephemeral. For persistent deployment, do not rely on the default local SQLite file on Render; use PostgreSQL via the supplied Blueprint. SQLite is intentionally the zero-dependency *local* default.

## API endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/bootstrap` | Current demo user, accounts, owned/shared docs, CSRF token |
| `POST` | `/api/switch` | Switch between seeded demo personas |
| `GET` | `/api/documents` | List accessible documents |
| `POST` | `/api/documents` | Create a document |
| `GET` | `/api/documents/{id}` | Read accessible document |
| `PATCH` | `/api/documents/{id}` | Save title/content with `revision` |
| `POST` | `/api/documents/{id}/share` | Owner grants another demo user access |
| `DELETE` | `/api/documents/{id}/share/{user_id}` | Owner revokes access |
| `POST` | `/api/import` | Multipart UTF-8 `.txt` file upload |
| `GET` | `/health` | Simple health check |

All writes require `X-CSRF-Token` obtained through `/api/bootstrap`. Sessions are signed, HttpOnly cookies, but identity switching is deliberately public in demo mode.

## Deliberately excluded

Real authentication/invitations, live multi-cursor editing, comments, document version history, binary attachments, `.docx` ingestion, PDF export, and advanced Google Docs formatting. This is a narrowly scoped, reviewer-friendly product slice.
